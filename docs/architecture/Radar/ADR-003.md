# ADR-003 — Provider Synchronization Engine (PSE)

**Projeto:** OSFlow ERP Imobiliário
**Estado:** Aprovado
**Versão:** 1.0
**Data:** 02/08/2026
**Autor:** Equipa OSFlow

---

# 1. Contexto

Após a consolidação da arquitectura do Radar (ADR-002), o sistema passou a suportar correctamente:

* Paginação SQL
* KPIs independentes da paginação
* Filtros SQL
* Repository como única fonte de dados

O próximo passo da evolução consiste em permitir que múltiplos providers (Imovirtual, OLX, Idealista, Casa Sapo, XML, APIs externas, etc.) executem sincronizações de forma uniforme.

Actualmente cada provider executa o seu processo internamente, sem um contrato único de estados nem um mecanismo padronizado de comunicação com a interface.

Esta abordagem dificultará:

* expansão para novos providers;
* reutilização de componentes;
* monitorização;
* demonstrações SaaS;
* manutenção.

---

# 2. Problema

Cada provider poderá possuir:

* tempos diferentes;
* número de anúncios diferente;
* etapas diferentes;
* regras específicas.

Sem um contrato comum, cada integração tenderá a implementar:

* mensagens diferentes;
* loaders diferentes;
* estados diferentes;
* UX diferente.

O resultado será uma experiência inconsistente.

---

# 3. Decisão

Será criado o **Provider Synchronization Engine (PSE)**.

O PSE será responsável por normalizar toda a comunicação entre:

```
Provider

↓

Motor de Sincronização

↓

Eventos

↓

UI
```

O provider apenas executa a sincronização.

O PSE controla todo o ciclo de vida.

---

# 4. Arquitectura

```
ImovirtualProvider

OLXProvider

IdealistaProvider

CasaSapoProvider

        │

        ▼

Provider Synchronization Engine

        │

        ▼

Progress Events

        │

        ▼

SyncProgressModal
```

---

# 5. Ciclo de Vida

Todo provider deverá seguir obrigatoriamente o seguinte workflow:

```
idle

↓

preparing

↓

connecting

↓

fetching

↓

processing

↓

saving

↓

finalizing

↓

completed
```

Em caso de erro:

```
failed
```

Nunca poderão existir estados personalizados.

---

# 6. Eventos

Cada alteração de estado gera um evento.

Modelo oficial:

```ts
interface SyncProgressEvent {

    provider: string;

    phase:
        | "idle"
        | "preparing"
        | "connecting"
        | "fetching"
        | "processing"
        | "saving"
        | "finalizing"
        | "completed"
        | "failed";

    message: string;

    processed: number;

    total: number;

    imported: number;

    updated: number;

    ignored: number;

    errors: number;

    startedAt: Date;

    finishedAt?: Date;

}
```

---

# 7. Modal Oficial

Será criado um componente único.

```
SyncProgressModal
```

Nenhum provider poderá implementar modais próprios.

---

# 8. Regras do Modal

Durante sincronização:

✔ bloqueia toda a interface

✔ impede clique exterior

✔ impede ESC

✔ impede botão fechar

✔ impede nova sincronização

✔ impede navegação

O utilizador apenas acompanha a execução.

# 10. Conclusão

Quando terminar:

```
✓ Sincronização concluída

18 novas oportunidades

6 actualizadas

1826 sem alterações
```

O estado permanece visível por aproximadamente 1 segundo.

Depois:

```
reload()

↓

actualizar KPIs

↓

actualizar tabela

↓

fechar modal
```

O utilizador nunca deverá clicar em "Fechar".

---

# 11. Suporte Multi-Provider

O modal deverá suportar múltiplos providers sem alterações estruturais.

Exemplo:

```
✓ Imovirtual

⏳ OLX

Idealista

Em espera

Casa Sapo

Em espera
```

O componente permanece exactamente igual.

---

# 12. Contrato dos Providers

Cada provider deverá implementar apenas:

```ts
startSync()

stopSync()

getProgress()
```

Toda a gestão visual pertence ao PSE.

---

# 13. Reload

O reload do Radar será executado apenas quando:

```
phase == completed
```

Nunca durante:

* fetching
* processing
* saving

Evita recarregamentos intermédios e inconsistências na UI.

---

# 14. Tratamento de Erros

Se ocorrer erro:

```
phase = failed
```

O modal deverá apresentar:

```
Não foi possível concluir a sincronização.

Provider:

Imovirtual

Motivo:

<mensagem técnica simplificada>
```

Disponibilizando apenas:

```
Fechar
```

Sem reload automático.

# 16. Benefícios

## Técnicos

* contrato único
* desacoplamento UI/Provider
* reutilização
* manutenção simplificada
* novos providers sem alterações na UI

## UX

* feedback em tempo real
* bloqueio seguro durante operações críticas
* experiência consistente
* percepção de performance
* redução de incerteza para o utilizador

## SaaS

* demonstrações mais profissionais
* comportamento uniforme em todas as integrações
* base preparada para processamento paralelo ou sequencial de múltiplos providers

---

# 17. Regras Arquiteturais

É proibido:

* criar loaders específicos por provider;
* implementar modais próprios;
* atualizar diretamente a UI a partir do provider;
* executar `reload()` durante a sincronização.

Toda a comunicação deverá passar obrigatoriamente pelo **Provider Synchronization Engine (PSE)**.

---

# 18. Critérios de Homologação

A implementação do PSE será considerada homologada quando:

* ✓ o modal bloquear completamente a interface durante a sincronização;
* ✓ todas as fases do workflow forem apresentadas corretamente;
* ✓ os contadores forem atualizados de forma consistente;
* ✓ o `reload()` ocorrer apenas após `completed`;
* ✓ a mesma infraestrutura funcionar com pelo menos dois providers sem alterações no componente `SyncProgressModal`;
* ✓ nenhum provider implementar lógica de interface própria.

---

## Observação estratégica

Este ADR estabelece um padrão que vai além do Radar. O **Provider Synchronization Engine** passa a ser uma infraestrutura transversal do OSFlow. Isso significa que qualquer operação longa e crítica do sistema poderá reutilizar exatamente o mesmo mecanismo de estados, progresso e UX, reduzindo duplicação de código e garantindo uma experiência consistente em toda a plataforma.
