# ADR-002
# OSFlow ERP Imobiliário
# Consulta SQL Unificada do Radar

**Status:** Aprovado para implementação
**Versão:** RC1.5.7
**Data:** 01/08/2026

---

# 1. Problema identificado

Durante a implementação da paginação SQL foram identificadas regressões sucessivas que demonstraram uma dependência arquitectural entre:

- Paginação
- Filtros
- KPIs
- Ordenação
- Snapshot

Estas funcionalidades não podem ser implementadas isoladamente.

Qualquer implementação parcial produz resultados incorrectos.

---

# 2. Princípio Arquitectural

A interface (React) nunca deverá calcular o universo de dados.

A interface apenas apresenta o resultado produzido pelo Repository.

Toda a inteligência pertence ao backend de acesso aos dados.

---

# 3. Fonte única de verdade

A única fonte de verdade passa a ser:

RadarRepository.getPage()

Nenhum outro componente poderá calcular:

- paginação
- filtros
- totais
- KPIs

# 6.1 Fonte dos Filtros (NOVO)

A origem das listas de filtros é independente da origem dos dados da tabela.

É proibido construir opções de filtros a partir de:

- snapshot.rows
- snapshot.opportunities
- tableRows
- qualquer subconjunto paginado

Os filtros deverão representar sempre o universo completo de dados disponível para a empresa.

---

Será criada uma nova responsabilidade no Repository.

RadarRepository.getFilterOptions(filters)

Responsável por devolver exclusivamente os valores distintos necessários para alimentar os controlos da UI.

Exemplo:

{

districts,

cities,

providers

}

Cada lista deverá ser obtida através de SQL utilizando DISTINCT.

Exemplo:

SELECT DISTINCT district

WHERE empresa_id = :empresa

AND provider_active = true

ORDER BY district

Os filtros activos deverão ser considerados quando fizer sentido.

Exemplo:

Se o utilizador seleccionar:

Distrito = Porto

A lista de cidades deverá conter apenas cidades existentes dentro desse distrito.

Nunca poderão ser utilizadas apenas as cidades da página corrente.

---

React não poderá calcular listas de filtros.

React apenas renderiza as listas devolvidas pelo Repository.

# 13. Regra obrigatória para o Copilot

Antes de alterar qualquer ficheiro deverá:

1. Diagnosticar impactos.

2. Identificar dependências.

3. Confirmar o contrato entre camadas.

4. Apenas depois efectuar alterações.

Caso identifique quebra do contrato deverá interromper a implementação e justificar tecnicamente.

Não deverá criar soluções temporárias, duplicar regras de negócio nem introduzir lógica paralela.

Concordo plenamente. Neste momento, o ADR-003 foi homologado com um PSE baseado em eventos em memória. Com a decisão de evoluir para uma arquitetura baseada em **Jobs persistentes**, o ADR deve ser **evoluído**, não substituído.

Eu não alteraria as secções já aprovadas. Acrescentaria uma nova revisão arquitetural, preservando o histórico das decisões.

# ADR-003 — Revisão 1 (RC1.6.0)

## 19. Persistência do Estado de Sincronização

### Contexto

A versão inicial do Provider Synchronization Engine (PSE) foi concebida para comunicar eventos entre o motor de sincronização e a interface através de um mecanismo de eventos em memória.

Esta abordagem foi suficiente para:

* sincronizações de curta duração;
* um único provider;
* feedback imediato ao utilizador.

Contudo, para suportar múltiplos providers, sincronizações longas, recuperação após refresh da página, monitorização e evolução SaaS, tornou-se necessário persistir o estado da sincronização.

---

## 20. Nova Fonte Oficial da Verdade

O estado da sincronização deixa de existir apenas em memória.

A fonte oficial passa a ser:

```text
provider_sync_jobs
```

O PSE deixa de ser responsável por manter estado.

Passa apenas a consumir e distribuir eventos.

---

## 21. Nova Arquitetura

```text
Frontend

        │

        ▼

ProviderSyncEngine

        │

        ▼

provider_sync_jobs

        ▲

        │

Edge Function

        ▲

        │

Provider
```

O fluxo deixa de depender da permanência do utilizador na página.

---

## 22. Provider Job Engine

É introduzido um novo componente:

```text
Provider Job Engine (PJE)
```

Responsabilidades:

* criar Job;
* actualizar progresso;
* actualizar métricas;
* concluir Job;
* cancelar Job;
* marcar falha.

O PJE será utilizado por todos os providers.

---

## 23. provider_sync_jobs

A tabela oficial deverá conter, no mínimo:

```text
id

empresa_id

provider

status

phase

message

processed

total

imported

updated

ignored

errors

started_at

updated_at

finished_at

execution_seconds

metadata (jsonb)
```

Esta tabela passa a ser o contrato oficial entre backend e frontend.

---

## 24. Responsabilidades

### Provider

Responsável apenas por:

* obter anúncios;
* processar dados;
* informar progresso ao PJE.

Nunca comunica directamente com React.

---

### Provider Job Engine

Responsável por:

* persistir progresso;
* actualizar métricas;
* gerir ciclo de vida;
* produzir estado oficial.

---

### Provider Synchronization Engine

Responsável por:

* observar alterações do Job;
* converter estado persistido em eventos;
* distribuir eventos para a UI.

Não mantém estado próprio.

---

### Interface

Responsável apenas por:

* observar o PSE;
* actualizar componentes visuais.

Nunca comunica directamente com providers.

---

## 25. Persistência

A sincronização deverá continuar válida mesmo quando:

* o utilizador actualizar a página;
* abrir outro separador;
* iniciar sessão noutro computador;
* a sincronização demorar vários minutos.

Ao voltar ao Radar, a UI deverá recuperar automaticamente o estado do Job activo.

---

## 26. Múltiplos Providers

A arquitectura deverá suportar simultaneamente:

```text
Job 001

Imovirtual

Running

----------------

Job 002

OLX

Running

----------------

Job 003

Idealista

Queued
```

Sem necessidade de alterar o `SyncProgressModal`.

---

## 27. Evolução do SyncProgressModal

O modal deixa de depender exclusivamente dos eventos emitidos pelo provider.

Passa a representar o estado persistido do Job.

Os eventos do PSE tornam-se uma projeção do estado existente em `provider_sync_jobs`.

---

## 28. Benefícios Arquiteturais

A adoção de Jobs persistentes permite:

* recuperação automática após refresh;
* histórico completo de sincronizações;
* execução de sincronizações longas;
* monitorização administrativa;
* métricas de desempenho por provider;
* suporte natural a múltiplos providers;
* preparação para execução em background.

---

## 29. Compatibilidade

Esta revisão **não invalida** a implementação homologada da RC1.5.8.x.

O `ProviderSyncEngine`, o `SyncProgressEvent` e o `SyncProgressModal` permanecem válidos.

A alteração consiste apenas em substituir a origem dos eventos:

**Antes**

```text
Provider
        │
        ▼
ProviderSyncEngine
        ▼
SyncProgressModal
```

**Depois**

```text
Provider
        ▼
Provider Job Engine
        ▼
provider_sync_jobs
        ▼
ProviderSyncEngine
        ▼
SyncProgressModal
```

O contrato da UI permanece inalterado, preservando a compatibilidade com as RCs já homologadas.

---

# Observação Estratégica

Esta revisão transforma o PSE de um **orquestrador com estado** para um **orquestrador baseado em eventos persistidos**, aproximando a arquitetura do OSFlow de plataformas SaaS de maior escala. A principal vantagem é que a interface deixa de depender da execução contínua do cliente, permitindo sincronizações resilientes, auditáveis e reutilizáveis para qualquer provider ou operação longa do sistema.
